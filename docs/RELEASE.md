## Phase 10: що завершено

- Порожні, завантажувальні й помилкові стани всіх основних екранів, скелетони,
  повтор запиту й повідомлення про невдалі записи/видалення. Для помилок UI або завантаження JS-вкладок є ErrorBoundary із відновленням. Мережеві помилки
  тепер нормалізуються в `ApiError`, тож невдалий Stop більше не залишається без повідомлення.
- Backend повертає локалізовний `validation_error`, не відображаючи ввід користувача
  або секрети у відповідях; UI має переклади помилок входу, мережі й rate limit.
- Модальні вікна: Escape, утримання й повернення фокуса, `aria-modal`, блокування
  прокрутки й `inert` для тла. Форми та SVG-графіки мають назви для допоміжних технологій.
- Heatmap відкриває поточний місяць, має клітинки 24 px та альтернативний вибір дати;
  майбутні дні вимкнені. Основні кнопки мають висоту щонайменше 44 px.
- Telegram theme/safe-area, нативна світла/темна палітра полів; читабельні помилки,
  підказки й попередження в світлій темі, підтримка reduced-motion.
- Типи API беруться з OpenAPI; відтворювана генерація без запущеного API.
- CI: ruff, pytest, PostgreSQL 16, міграції в обидва боки, контракт, typecheck,
  React-тести, build і синтаксис shell-скриптів.
- `staleTime`, розділення вкладок на окремі JS-чанки, вимірювання бандлів.
- Міграція `0007` додає складений індекс сну `(user_id, local_date)`.
  Індекси тренувань/стресу/екранного часу з попередніх фаз збережено.
- EXPLAIN ANALYZE перевірено на окремій PostgreSQL із 200 синтетичними акаунтами
  і 12 000 ночей; усі чотири вибірки використовували Index Scan. Локальний час
  виконання: 0.056–0.092 мс, без мережі й підготовки плану. Це не вимірювання Oracle.
  Повні плани: [PERFORMANCE.txt](PERFORMANCE.txt).

## Phase 11: що реалізовано

### Дані та приватність

- `GET /api/v1/me/export`: JSON усіх дат, відкритих/завершених записів, профілю,
  інсайтів і метаданих активних/відкликаних токенів. Експорт виконується в одному
  `REPEATABLE READ` snapshot, включно з авторизацією. Хеші/секрети токенів,
  JWT та серверні секрети не експортуються.
- `DELETE /api/v1/me`, тіло `{"confirm": true}`: видалення поточного користувача
  із каскадом усіх шести таблиць. Старі JWT і токени Shortcuts втрачають доступ.
  Обидва ендпоінти приймають лише JWT, а не Shortcut-токен.
- Налаштування: завантаження JSON, підтвердження видалення окремим checkbox,
  пояснення наслідків і статус результату. Випадкові запити/refresh після видалення
  не створюють акаунт заново; повторний вхід можливий через явне «Почати заново».
- Публічні `/privacy/uk` і `/privacy/en`, доступні без входу. Посилання є в
  застосунку й боті. Тексти позначено **чернеткою**, доки власник їх не переглянув.
- Немає рекламних трекерів, сторонньої аналітики чи LLM-обробки користувацьких записів.

### Бот і захист

- `/help`, `/privacy`, локалізований список команд, повний і короткий описи бота.
- Обмеження входу через Telegram: 30 запитів за хвилину на адресу, включно з невдалими.
- Довіряти `X-Forwarded-For` можна лише визначеному reverse proxy; прямий клієнт
  не може обійти ліміт зміною заголовка. Compose закріплює IP Caddy `172.30.28.2`.
- Production-конфігурація відхиляє короткі JWT/webhook-секрети, dev-вхід та HTTP URL.
- API-відповіді мають `Cache-Control: no-store`; Caddy додає security headers і CSP.
- `/health` перевіряє PostgreSQL: HTTP 200 за успіху, 503 за відмови/таймауту.
- Docker: ротація локальних логів і healthcheck бекенду. Один процес бекенду збережено.

### Експлуатація

- `deploy/backup.sh`: атомарний custom-format `pg_dump`, перевірка `pg_restore --list`,
  SHA-256, приватні дозволи, ротація власних dump-файлів. Можлива копія на налаштований
  власником rclone crypt remote через `BACKUP_REMOTE`.
- `deploy/restore-drill.sh`: відновлення **лише в нову тимчасову БД**, перевірка checksum,
  міграцій і всіх таблиць; production-база не перезаписується.
- `backend/scripts/compare_restore.py`: точне порівняння всіх рядків і ревізії між
  спокійною вихідною базою та окремою відновленою `_test` базою.
- `deploy/release-check.sh`: перевірка Compose, стану контейнерів, health і міграції.
- Інструкції для моніторингу, SSH, системних оновлень, ротації секретів та бета-перевірки.

## Запуск локально

З кореня проєкту використай наявний Docker Compose і dev `.env` з `.env.example`.

```powershell
docker compose up --build
```

В окремих терміналах:

```powershell
cd backend
python -m pip install -e ".[dev]"
python -m pytest
```

```powershell
cd frontend
npm ci
npm run typecheck
npm test
npm run dev
```

Без `TEST_DATABASE_URL` два справжні PostgreSQL-тести пропускаються. Для їх запуску
використовуй окрему мігровану БД з назвою, що закінчується `_test`.
Демо-генератор лишається лише для порожнього dev-акаунта, див. [PHASE9.md](PHASE9.md).

## Перед деплоєм на Oracle

1. Зберегти поточний production backup і виконати restore drill. Старі `.sql.gz`
   бекапи не видаляти: новий скрипт працює з `.dump`, а їх ротацію треба вирішити окремо.
2. Перенести код у власний Git-репозиторій, запустити CI й переглянути результати.
3. У `.env.prod` залишити власні реальні секрети; JWT та webhook мають бути ≥32 байт/символів.
   Перевірити нову Docker-підмережу `172.30.28.0/24`: якщо зайнята, змінити її й
   IP Caddy / `TRUSTED_PROXY_IPS` разом. Backend і DB не публікуються назовні.
4. Переглянути політику: власник, контакт, правова підстава, фактичні провайдери/регіони
   й строки зберігання локальних та віддалених копій. Заповнити `PRIVACY_OWNER`,
   `PRIVACY_CONTACT`, відредагувати потрібні тексти в обох локалях; лише після цього
   встановити `PRIVACY_APPROVED=true`. Це потребує перебудови фронтенду.
5. На сервері виконати:

```bash
cd ~/sleepguide
git pull
dc up -d --build
bash deploy/release-check.sh
dc logs --tail 40 backend
```

Має бути ревізія `0009`; використовуй свій `dc`, який підключає `.env.prod` і prod-compose.
Контейнери не збиралися й не запускалися тут: перевірено їхню конфігурацію, а не ARM-образи.

## Резервні копії й відновлення на сервері

```bash
cd ~/sleepguide
bash deploy/backup.sh
bash deploy/restore-drill.sh /absolute/path/to/sleepguide_TIMESTAMP.dump
```

За замовчуванням нові копії лежать у `sleepguide/backups/` (ігнорується Git).
Можна задати `BACKUP_DIR` на захищений диск і `BACKUP_RETENTION_DAYS` (типово 14).
Налаштувати нічний запуск у cron/systemd і контролювати його exit code та свіжість копій.

Для копій поза VM власник налаштовує **rclone crypt** над власним хмарним сховищем;
ключі та конфігурацію тримати поза Git, із правами 600. Приклад після такого налаштування:

```bash
BACKUP_REMOTE='sleepguide_crypt:backups' bash deploy/backup.sh
```

Перевірити отримання й дешифрування копії з іншого пристрою. Для віддалених копій
налаштувати строк зберігання/життєвий цикл: локальна ротація не видаляє remote-файли.
Жодного віддаленого сховища або передавання приватних даних у цій роботі не налаштовано.
Після відновлення старої копії повторно виконати зафіксовані запити на видалення даних;
не відновлювати користувачів, які просили видалити їхні записи.

## Моніторинг і захист VM

- Підключити обраний власником uptime-monitor до `https://sleepmaxxing.pp.ua/health`
  з перевіркою HTTP 200; сповіщати про відмову. Користувацьких даних у відповіді немає.
- Контролювати свіжість бекапів, місце на диску, `dc ps`/health і помилки нагадувань.
- Перевірити `unattended-upgrades` у власній Ubuntu та журнал оновлень; визначити
  вікно перезавантаження. На VM ці налаштування тут не змінювалися.
- SSH: спочатку перевірити вхід по ключу в новій сесії й доступ до Oracle console.
  Після цього налаштувати `PasswordAuthentication no`, `KbdInteractiveAuthentication no`,
  `PermitRootLogin no` у відповідному sshd snippet, перевірити `sudo sshd -t` і
  `sudo sshd -T`; лише потім reload SSH і ще раз перевірити нову сесію.
  Наявну сесію не закривати до перевірки. Врахувати overrides cloud-init і порядок snippet-ів.
- Секрети: старий бот-токен із чату відкликати через BotFather, новий — лише в `.env.prod`;
  `dc up -d --force-recreate backend`. JWT-ротація завершує поточні сесії; webhook-secret
  потребує перезапуску з повторним setWebhook; DB-пароль — узгоджено змінити у PostgreSQL
  і `.env.prod`, перевірити доступ, потім відновити API. Не друкувати секрети в логах.
- Домен і білінг Oracle: автопродовження, budget alerts і рішення Pay As You Go приймає власник.

хмарного backup-сховища й телефонів у цій роботі не було. Артефакт — повний код
та перевірені локальні процедури, а не підтвердження production-релізу.
